# BLACK GOLD｜完整功能与使用说明

> 本文件区分「目前网页原型已能操作的功能」与「数据库已设计、但尚未接通的功能」。页面出现某个入口，不代表云端、AI 或跨手机能力已经完成。

## 1. 产品定位

BLACK GOLD 是一个面向两个人的私人健康管理系统。目标是让每个人分别记录身体、饮食、饮水、运动与睡眠，再用长期数据观察变化；双方可以在明确授权后分享指定类别的进度，但个人原始健康记录默认保持私密。

产品采用黑金视觉风格。设计原则：
- 两个独立个人资料空间，不把双方记录混在一起。
- 健康数据以长期趋势为主，不因单日变化作过度判断。
- 资料分享按类别授权，允许随时撤销。
- 数据备份、删除和隐私控制必须清楚可见。
- AI 建议应说明依据与不确定性，不替代医生诊断。

## 2. 网页版目前可操作的功能

### 2.1 总览 Dashboard
**用途：** 快速查看当天的健康记录。

**使用方式：**
1. 打开「总览」。
2. 页面显示当前个人的最近晨起体重、今日饮食热量、今日饮水量和今日运动分钟数。
3. 「最近记录」显示近期体重、运动和饮食记录。
4. 使用快捷按钮进入体重、饮食或运动页面。

**当前状态：** 数据从当前浏览器本地记录读取；没有云端同步。今日提示是固定的基础提示，不是 AI 个性化分析。

### 2.2 身体数据与体重
**用途：** 记录体重与身体组成，观察长期变化。

**可记录项目：**
- 体重（kg）、日期、晨起或睡前。
- 体脂率、肌肉量。
- 腰围、腹围。

**使用方式：**
1. 进入「身体」。
2. 在体重卡片输入体重，选择晨起或睡前，并选择日期。
3. 按「保存体重」。
4. 在身体组成卡片填写实际测量到的体脂、肌肉量、腰围或腹围；没有数据的项目留空。
5. 在下方查看体重历史。

**注意：** 当前网页已保存体重和身体组成记录，但尚未提供完整趋势图、BMI 自动分析、身体照片进度比较或智能体脂秤同步。不要填写猜测数据。

### 2.3 饮食记录
**用途：** 记录每餐吃了什么，以及大致营养摄入。

**可记录项目：**
- 食物名称。
- 热量（kcal）。
- 蛋白质、碳水化合物、脂肪（g）。
- 份量与备注。

**使用方式：**
1. 进入「饮食饮水」。
2. 可以拍摄食物照片作当下预览。
3. 输入食物名称与实际份量。
4. 根据包装营养标签、可靠资料或人工估算填写热量与营养素。
5. 按「加入饮食记录」，之后可查看当天及历史记录。

**当前限制：** 照片目前只在页面预览，不会上传，也不会随记录保存；AI 食物识别、自动估算份量、条码扫描和自动营养数据库尚未接入。手动填写的热量不代表系统已验证其准确性。

### 2.4 饮水记录
**用途：** 统计一天实际喝下的水量。

**使用方式：**
1. 在「饮食饮水」的饮水卡片输入本次喝下的毫升数。
2. 可填写杯子或水瓶备注。
3. 按「记录饮水」。
4. 总览会累加当天饮水量，历史区显示每次记录。

**当前限制：** 水瓶照片只是预览，系统不能单凭照片准确知道容器容量或实际喝下多少；需要用户输入毫升数。

### 2.5 运动与活动
**用途：** 记录运动种类、时间、距离和训练感受。

**目前预设项目包括：**
步行、跑步、骑脚车、自由泳、蛙泳、仰泳、蝶泳、重量训练、器械训练、核心训练、瑜伽、普拉提、拉伸、羽毛球、篮球、足球、网球、爬山、徒步及居家运动。

**使用方式：**
1. 进入「运动」。
2. 选择运动项目。
3. 输入运动分钟数；有可靠数据时可填写热量消耗与距离。
4. 选择轻松、中等或较高强度。
5. 填写训练备注后保存。
6. 可新增自定义运动项目，之后会出现在当前个人的项目清单中。

**当前限制：** 热量消耗是手动输入，不是设备实测或 AI 自动计算。步数、心率和活动数据尚未接入穿戴设备。

### 2.6 游泳专项记录
**用途：** 记录泳池训练内容，计算距离与有效游动速度。

**可记录项目：**
- 泳姿：自由泳、蛙泳、仰泳、蝶泳、混合泳、打腿练习、单手划水练习等。
- 泳池长度（m）。
- 完成趟数（每次单程计一趟）。
- 整次训练总时间。
- 休息总时间。
- 系统根据泳池长度 × 趟数计算距离，并以扣除休息后的有效时间计算平均速度。

**使用方式：**
1. 选择游泳项目。
2. 填写泳姿、泳池长度和趟数。
3. 填写整次训练的总分钟数，以及休息分钟数。
4. 保存后查看距离、趟数、休息时间和平均速度。

**计算规则：**
- 游泳距离（m）= 泳池长度（m）× 趟数。
- 有效游动时间（分钟）= 训练总时间 − 休息时间。
- 平均速度（km/h）= 距离（km）÷ 有效游动时间（小时）。

请确保趟数采用「单程一趟」的统一规则；若泳池长度或趟数输入错误，计算结果也会错误。

### 2.7 睡眠记录
**用途：** 记录睡眠时段与主观质量，协助观察休息习惯。

**使用方式：**
1. 进入「睡眠」。
2. 输入入睡时间与起床时间。
3. 选择很好、普通或不好。
4. 可备注半夜醒来、难入睡或疲劳等情况。
5. 保存后查看睡眠历史。

**当前限制：** 系统按开始和结束时间计算时长；尚未连接手表睡眠阶段、血氧或心率数据。恢复建议目前是一般性文字，不是医学诊断或 AI 分析。

### 2.8 双人空间与共同目标
**用途：** 让两个人在保留各自隐私的情况下设定共同挑战。

**目前网页原型可操作的内容：**
- 切换「我的页面」与「宝宝的页面」。
- 两个本地资料分别保存体重、身体、饮食、饮水、运动、睡眠和教练偏好。
- 查看双方本地记录数量。
- 设置本周共同目标，例如各自完成三次运动。

**当前限制：** 这只是同一浏览器里的本地双人演示，不是真正的两个账号，也没有跨手机同步、邀请链接或服务器权限验证。共同目标目前存于同一浏览器。

### 2.9 教练偏好与个人设置
**用途：** 保存每个人希望教练采用的沟通方式。

**可设置项目：**
- 教练风格：全能型、温和鼓励型、数据分析型、严格训练型。
- 语言偏好：中文、马来语或英语。
- 工作与生活资料：工作性质、作息、运动限制等。

**当前限制：** 这些偏好目前只保存在本地，AI 教练尚未接入，因此不会产生真正的个性化 AI 对话。

### 2.10 数据备份与清除
**用途：** 让用户保留自己的记录，并在需要时清理本机资料。

**使用方式：**
- 「导出数据备份」：下载 JSON 格式备份。
- 「导入备份」：选择之前导出的 JSON 文件恢复记录。
- 「清除此浏览器中的全部本地记录」：清除当前浏览器里两个人的本地记录。此操作不可撤销，执行前应先备份。

**重要：** 清除浏览器资料、换手机或更换浏览器可能导致本地数据无法继续访问；在云端同步尚未完成前，请定期自行导出备份。

## 3. 数据库已设计、但尚未接通的后端功能

当前 Supabase migration 草案包含以下数据结构或安全机制，代表开发设计方向，不代表用户已经可以在 APP 中使用：

### 3.1 个人账号与资料
- 用户个人资料、显示名称、出生日期、身高、时区与语言偏好。
- 新账号注册后自动建立个人资料的数据库触发器。

### 3.2 健康记录
- 目标与计划。
- 体重、身体组成、身体围度。
- 身体进度照片的私有储存路径。
- 食物、营养素与估算范围。
- 饮水。
- 日常活动、步数、运动训练与睡眠。
- 设备连接资料。
- AI 对话、洞察与日报/周报/月报。
- 提醒、通知及升级申请。

### 3.3 双人关系与授权
- 创建双人关系。
- 通过邀请令牌邀请另一位用户；邀请设计为七天过期。
- 接受或撤销邀请。
- 按类别授权，例如体重趋势、身体数据、步数、运动、营养摘要、饮水摘要、睡眠摘要、每周进度和成就。
- 授权可以撤销。
- 未授权时不应读取对方健康资料。

**重要：** 这些机制仍需在独立测试数据库里验证。不得把目前的数据库草案视为已部署或已通过安全审计。

### 3.4 私有照片储存
数据库设计了私有储存空间，目标是让用户的健康照片默认只由本人访问。共享照片需要额外明确设计与授权；当前网页照片预览不等于已上传到这个储存空间。

## 4. 未来规划中的 AI 与设备功能

以下属于后续开发目标，不是当前已启用的功能：

- AI 食物照片识别、份量估算、营养分析，并让用户确认后才写入记录。
- AI 训练照片/运动记录辅助识别。
- 根据连续数据生成体重、饮食、运动、睡眠和恢复趋势分析。
- 个性化目标、训练安排、饮食建议与提醒。
- 每日、每周、每月报告。
- 语音教练；声音模仿或克隆必须另行取得明确授权并评估安全性。
- 连接智能手表、体脂秤及 Android Health Connect；每个品牌和型号都要实测兼容性，不能仅凭品牌名称保证支持。
- 双手机账号登录、邀请、逐项授权和实时撤销。
- 正式云端备份、账号删除和资料导出。

## 5. Android 版本现状

目前 Android 工程仍是基础测试界面：
- 黑金主题。
- 总览、体重、饮食、运动、我的五个底部入口。
- 「我」与「宝宝」的本机页面切换。
- 体重输入与本机 SharedPreferences 保存。

饮食、运动等页面仍是开发占位；Android 版尚未接通 Supabase 云端账号、AI、双人共享、设备数据或完整记录流程。现阶段不能称为正式完整版本。

## 6. 隐私、安全与发布原则

1. 健康数据默认属于个人，不默认向伴侣公开。
2. 每个共享类别必须由资料拥有者主动授权，并能撤销。
3. 客户端只能使用公开 Publishable Key；Secret/Service Role Key 和数据库密码绝不能放进 App 或公开仓库。
4. 正式上线前必须验证账号隔离、数据库行级权限、邀请流程、照片访问权限、备份与删除流程。
5. 先在独立开发/测试项目验证 migration，不直接在正式项目试跑未经验证的 SQL。
6. 任何尚未完成或未测试的功能，必须在页面与说明中标注状态。
7. 健康建议用于日常管理，不代替医生诊断；异常或持续不适应寻求专业医疗意见。

## 7. 开发阶段判断

- **目前可操作：** 网页本地记录原型、双人本地档案切换、游泳距离计算、本地 JSON 备份/导入/清除。
- **正在开发验证：** Supabase 数据库结构与权限；GitHub 自动化本地数据库测试。
- **尚未接通：** 网页云端账号、跨设备同步、真正双人邀请与授权读取、AI 服务、照片上传、设备同步、完整 Android 功能。
- **正式发布前必须完成：** 数据库测试与安全验证、端到端测试、隐私/删除流程、真实设备测试和用户验收。
